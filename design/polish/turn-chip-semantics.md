## 1. 裁决摘要（K1）

> **裁决：采用 turn-based（行动权归属）语义。**
> 金色角标**只在「该座位当前拥有行动权」时出现**；任何无行动权的状态，一律不显示角标。
> 原 `idle`（等待）态**整体废弃**，其承载的信息交还给 `<em>`（上手动向）与 `<span>`（余牌 / 名次）两条既有通道。

### 1.1 四条决定性理由

**理由一 · 冗余通道不能自相矛盾（最致命）**

角标的存在理由是「`.seat.active` 原先只靠金色描边传达『轮到谁』，违反『不得仅靠颜色传达信息』」。也就是说，角标是 `active` 的**第二重编码**。

而现状恰恰是：金环说「轮到你」，角标说「等待」。两条通道互相打架时，结果比只有一条通道更糟——用户无法判断该信哪个。**冗余通道的第一原则是同真同假，不是互补。**

**理由二 · 新手引导价值：要回答的问题是「现在轮到谁」**

新手在牌桌上的第一问是「轮到谁了」，第二问才是「我在等谁」。第二问是第一问的补集，可被推导；第一问不可被推导。把不可推导的信息放在唯一可见的角标上，是正确分配。

wait-based 语义下，4 张卡有 3 张常年挂着「等待」，唯一有价值的那 1 张反而在关键时刻说错——信息密度与信息价值成反比。

**理由三 · 掼蛋的节奏感：轮转快、等待短，噪声必须低**

掼蛋单副 27 张、四家轮转，一个 trick 常在数秒内走完一轮，电脑行棋间隔 750ms（`app.js` `schedule()`）。wait-based 下三张「等待」角标会随轮转不停迁移闪烁；turn-based 下**同一时刻全局最多一个角标**（唯一例外是双贡，见 §3 S3）。这既符合「克制的视觉调性」，也符合动效规范里「只动合成属性、控制并发」的约束。

**理由四 · 可证伪的不变量，从根上消灭这一整类缺陷**

turn-based 给出一个单布尔不变量：

```
角标可见  ⟺  .seat.active（金环可见）  ⟺  该座位可立即行动
```

「可立即行动」在引擎里是**单次判定的事实**（`phase==='play'&&turn===i`，或 `phase==='return'&&returns.some(r=>r.from===i)`），不需要对历史做推断。

而 wait-based 的 `idle` 需要从 `game.last[]` 反推「他上一手是不是过牌」——`last[]` 是**跨 trick 残留的历史字段**（`engine.js:41` 只在三家全过、清桌时才 `g.last=[null,null,null,null]`），任何历史反推都会遇到「历史尚未刷新但状态已变」的窗口。**这不是实现疏忽，是语义选型把不必要的复杂度引入了渲染层。** 换语义后，这一整类 bug 在结构上不可能再发生。

### 1.2 附带发现：现有 `idle` 态自身二次违反无障碍要求

`index.html` 内联 CSS：

```css
.seat .turn-chip{ ... background:var(--gold); ... }
.seat.idle .turn-chip{background:#cbbfa6}
```

「轮到」与「等待」两个角标的**唯一**视觉差异是背景色（金 `#eabd65` vs 米 `#cbbfa6`）。这是**纯颜色传达信息**——正是当初引入角标要消灭的那种违规。

采用本文裁决后：三种角标各有**不同文字**（领出 / 轮到 / 还贡），文字本身就是第二通道，颜色退化为纯装饰。**建议三种角标统一用金色**，`#cbbfa6` 规则直接删除。

## 2. 「重新领出」情形的文案裁决（问题 2）

### 2.1 先厘清：被复现的缺陷其实落在**跟牌**态，而提问指向**领出**态

两者都源于同一个 `idle` 判定，但文案处理不同：

| 情形 | 引擎状态 | 正确语义 |
|---|---|---|
| 甲过牌 → 乙出牌（清 `passed`）→ 丙过牌 → 回到甲 | `top !== null` | 甲**可压牌或不要** |
| 甲过牌 → 其余三家依次过牌 → 清桌，甲重新获得领出权 | `top === null` | 甲**必须出牌，不能不要** |

关键实现事实：**只要 `top === null`，该座位就是领出方**，`engine.js:41` 在清桌时统一 `g.top=null; g.passed=[]; g.last=[null,null,null,null]`。这个分支同时覆盖了三种来源：

1. 首副翻明牌定先手（`deal()` → `g.turn=翻牌持有者`，`top=null`）
2. 本 trick 三家全过，最后出牌者重新领出（`act()` → `g.turn=winner`，`top=null`）
3. **接风**：最后出牌者已走完，由对家接风（`act()` → `g.turn=(winner+2)%4`，`top=null`）

所以「重新领出」不需要专门的状态位——**`turn===i && top===null` 就是它**，且与接风、开局共用同一文案。这也是选型上更倾向于 turn-based 的地方：一个字段判定，三种来源自动正确。

我已在本地跑通验证：构造 `top={seat:2}` + `last[1].pass=true` + `turn=1`，旧判定输出「等待」（错误），新判定输出「轮到」（正确）；构造 `top=null` + `turn=1`，新判定输出「领出」。

### 2.2 文案裁决：**「领出」**

**采纳 A。**

| 方案 | 文案 | 字数 | 评估 |
|---|---|---|---|
| **A（采纳）** | **领出** | 2 | 与 `RULES.md`（「领出不能不要」「重新领出」「接风」）及 `#hint`（「轮到你领出，不能不要」）**同一套词汇**，零学习成本；2 字，宽度零风险 |
| B | 必须出 | 3 | 义务更直白，但丢掉「本轮第一个出牌」这一信息；语感偏命令，与「暖色会所」调性略冲 |
| C | 领出必出 | 4 | 信息最全，但生硬；4 字在 ≤560px 断点上会加剧 K2 裁切 |

**为什么「领出」已经足够传达「必须出牌」**：人类座位的 `#pass` 按钮在 `top===null` 时已被禁用（`app.js:58`：`$('#pass').disabled=game.phase!=='play'||game.turn!==0||!game.top`），`#hint` 亦输出「轮到你领出，不能不要」。**角标不必承担规则教学职责**，它只需标明「行动权归属 + 领出身份」。完整的义务说明交给不受宽度约束的 `aria-label`。

## 3. 完整状态机

### 3.0 判定优先级

各状态**互斥且有序**，下表即判定顺序，工程侧按序实现即可，无需额外优先级表：

```
S0 本副/本场结束   → phase === 'over'
S6 已走完         → finished.indexOf(i) >= 0
S3 还贡待办       → phase === 'return' && returns.some(r => r.from === i)
S7 还贡·待收贡    → phase === 'return' && returns.some(r => r.to === i)
S8 还贡·旁观      → phase === 'return'
S1 领出           → phase === 'play' && turn === i && !top
S2 跟牌           → phase === 'play' && turn === i &&  top
S4 已出牌         → phase === 'play' && top?.seat === i
S5 已过牌         → phase === 'play' && last[i]?.pass
S9 等待中         → 其余
```

> 注：`S3/S7/S8` 必须排在 `S1/S2` 之前——`return` 阶段 `g.turn` 指向的是**进贡方**（`engine.js:29` `g.turn=gifts[0].from`，供还贡后先出用），但还贡阶段实际拥有行动权的是**收贡方**（`returns[].from`）。若先判 `turn`，会错误地把角标挂到进贡方头上。

### 3.1 状态机表格

| ID | 状态 | 触发条件（`game` 字段） | 视觉文案 | `aria-label` 后缀 | 视觉提示（非颜色） | 角标 |
|---|---|---|---|---|---|---|
| **S1** | **领出**（必须出牌） | `phase==='play' && turn===i && !top` | **领出** | `轮到，领出，不能不要` | 金环 + 角标「领出」；人类座 `#hint`「轮到你领出，不能不要」、`#pass` 禁用 | 金 |
| **S2** | **跟牌**（可压可过） | `phase==='play' && turn===i && top` | **轮到** | `轮到，可压牌或不要` | 金环 + 角标「轮到」；人类座 `#play`/`#pass` 均可用 | 金 |
| **S3** | **还贡待办** | `phase==='return' && returns.some(r=>r.from===i)` | **还贡** | `轮到，需要还贡` | 金环 + 角标「还贡」；人类座 `#play` 文案变「确认还贡」、`#hint` 提示选牌 | 金 |
| **S4** | **已出牌**（等回应） | `phase==='play' && top?.seat===i && turn!==i` | —（无） | `等待其他玩家回应` | 无环无角标；`<em>` 显示所出牌型；`.table-cards` 归属该座 | — |
| **S5** | **已过牌**（本轮未结束） | `phase==='play' && last[i]?.pass && turn!==i && top` | —（无） | `已不要，等待中` | 无环无角标；`<em>` 显示「不要」 | — |
| **S6** | **已走完** | `finished.indexOf(i)>=0` | —（无） | `已走完` | 无环无角标；`<span>` 显示「头游 / 二游 / 三游 / 末游 / 双下」 | — |
| **S7** | **还贡·待收贡** | `phase==='return' && returns.some(r=>r.to===i)` | —（无） | `等待对方还贡` | 无环无角标；人类座 `#hint`「等待电脑牌友还贡」 | — |
| **S8** | **还贡·旁观** | `phase==='return'`（既非 `from` 也非 `to`） | —（无） | `等待中` | 无环无角标 | — |
| **S9** | **等待中**（非活动） | 其余（有手牌、无行动权） | —（无） | `等待中` | 无环无角标 | — |
| **S0** | **本副 / 本场结束** | `phase==='over'` | —（无） | `本副结束` / `本场结束`（`champion!==undefined` 时） | 无环无角标；`#summary` 展开结果 | — |

### 3.2 关于 S4 / S5 / S6 不显示角标的说明

提问中列出的三项（已过牌 / 已出牌 / 已走完）**均不显示角标**，这是裁决的直接推论，不是遗漏。理由：

- **S4 已出牌**：`<em>` 已显示所出牌型（如「对子」），`.table-cards` 亦带 `data-seat` 归属。加角标会与 `<em>` 重复。
- **S5 已过牌**：`<em>` 已显示「不要」。这正是缺陷的源头——`idle` 想表达的「他过牌了」本就由 `<em>` 承载，角标是多余的第二份，且写错了。**删掉它，信息一条不少。**
- **S6 已走完**：`<span>` 已从「余 N 张」切换为名次文本。「头游 / 二游 / 三游 / 末游 / 双下」本身就是非颜色的正向信号，满足无障碍要求，无需角标。

> 若后续确实想强化 S5 的视觉表达，**正确做法是给 `<em>` 加弱化样式**（如已过牌的「不要」降低透明度），而不是新增第二个角标——`<em>` 就是「上手动向」这条通道的既定载体，不要开第三条。

### 3.3 P2 可选项：「已还贡」（**建议本次不做，仅备案**）

提问中列出的「还贡阶段：已还贡」需要反推「谁曾是债务人」，因为 `giveBack()` 会直接把条目从 `returns` 中删除（`engine.js:31`），完成后**无法从 `returns` 判断谁还过**。

已验证可行的推导（60 副模拟、16 次 return 阶段采样，16/16 一致）：

```js
const initDebtors = g.result?.double ? g.previous.slice(0,2) : g.previous.slice(0,1);
const returned = g.phase==='return' && initDebtors.includes(i) && !g.returns.some(r=>r.from===i);
```

**建议本次不做的理由**：

1. 还贡阶段极短（电脑每手 750ms，双贡也不过约 1.5s），收益边际；
2. 打破「角标 ⟺ 有行动权」这一干净不变量，变成「有行动权 **或** 刚完成行动」；
3. 依赖 `previous` / `result.double` 两个**跨副持久字段**，未来引擎重构易被静默破坏；
4. 3 字文案会加剧 K2（≤560px 角标裁切）。

**若用户要求做**，文案用「已还贡」，视觉用弱化样式（文字已区分语义，故不违反色彩规则），并补一条回归断言。

## 4. `aria-label` 规范

### 4.1 关键点：aria 不受宽度约束，因此比视觉更具体

这是本次裁决的核心收益之一：**视觉受 4 字约束，只标行动权；`aria-label` 无宽度约束，可为每个座位输出正向、具体的语义。** 读屏用户因此能听到全部 9 种状态的区分，而视觉只保留最低噪声的行动权提示。

### 4.2 完整格式

```
{nickname} · {<span> 文本} · {<em> 文本} · {后缀}
```

沿用 `app.js:26` 现有 ` · ` 分隔符（TTS 会读作停顿）。后缀取自 §3.1 表格第 5 列，**恒非空**——这是相较现状的改进：旧实现在非活动座位上**不追加任何后缀**，读屏用户只能靠「没有后缀」反推，属于否定式信息。

### 4.3 各状态实例（以 seat0「你」为例）

| 状态 | 完整 `aria-label` |
|---|---|
| S1 领出 | `你 · 余 23 张 · 青松队 · 轮到，领出，不能不要` |
| S2 跟牌 | `你 · 余 23 张 · 对子 · 轮到，可压牌或不要` |
| S3 还贡 | `你 · 余 27 张 · 青松队 · 轮到，需要还贡` |
| S4 已出牌 | `你 · 余 20 张 · 同花顺 · 等待其他玩家回应` |
| S5 已过牌 | `你 · 余 23 张 · 不要 · 已不要，等待中` |
| S6 已走完 | `你 · 头游 · 顺子 · 已走完` |
| S7 待收贡 | `你 · 余 27 张 · 青松队 · 等待对方还贡` |
| S9 等待中 | `你 · 余 23 张 · 青松队 · 等待中` |
| S0 结束 | `你 · 二游 · 三带二 · 本副结束` |

### 4.4 两条无障碍补充要求

1. **角标 `<span>` 加 `aria-hidden="true"`**。`.seat` 已带 `aria-label`，理论上 AT 不会另读内部文本；加此属性是防御性的，避免个别 AT 回退到内容读取时把「领出」重复念两遍。
2. **不要给 `.seat` 加 `aria-live`**。轮转每 750ms 一次，live region 会持续刷屏。座位卡保持为被动可读元素，由用户主动 `Tab` 遍历即可。

## 5. 工程侧实现映射

改动集中在 `app.js` 的 `renderSeats()`（第 17–26 行）。**`active` 的计算方式完全不变**——它已经等价于「有行动权」，因此金环行为、R2 的 `::after` 轮转动画、`.seat.active::after{opacity:1}` 全部零影响，改动面比看上去更小。

### 5.1 新增两个纯函数（`app.js`，建议紧贴 `renderSeats()` 上方）

```js
/* 角标语义（见 design/polish/turn-chip-semantics.md）：
   金色角标 = 该座位当前拥有行动权。不变量：角标可见 ⟺ .seat.active ⟺ 可立即行动。
   唯一例外是双贡——两张卡同时显示「还贡」，因为还贡本身是并行的。 */
function chipText(i){
  if(game.phase==='return')return game.returns.some(r=>r.from===i)?'还贡':'';
  if(game.phase!=='play'||game.turn!==i)return '';
  return game.top?'轮到':'领出';
}
function chipAria(i,place){
  if(game.phase==='over')return game.champion!==undefined?'本场结束':'本副结束';
  if(place>=0)return '已走完';
  if(game.phase==='return')return game.returns.some(r=>r.from===i)?'轮到，需要还贡'
    :game.returns.some(r=>r.to===i)?'等待对方还贡':'等待中';
  if(game.turn!==i)return game.top?.seat===i?'等待其他玩家回应':game.last[i]?.pass?'已不要，等待中':'等待中';
  return game.top?'轮到，可压牌或不要':'轮到，领出，不能不要';
}
```

| `last[i]` | `last[i].pass` ⇒ S5；`last[i].p.type` ⇒ `<em>` 文本。**历史字段，不得用于行动权判定**（缺陷根源） | `engine.js:41,42` |
| `finished` | `indexOf(i)` ⇒ 名次 / S6 | `engine.js:33,42` |
| `returns` | `{from,to}`：`from`=收贡方（**还贡义务人**）、`to`=进贡方。`from` 判 S3，`to` 判 S7 | `engine.js:29,31` |
| `result.double` | 是否双下，影响名次文案与 P2 推导 | `engine.js:35` |
| `champion` | 本场是否已结束（S0 文案分叉） | `engine.js:37` |

> **易错点**：`returns` 的 `from` / `to` 方向与直觉相反——`from` 是**收贡方（头游/二游，欠一张还贡）**，`to` 是**进贡方（末游/三游，等着收牌）**。`engine.js:29` 的 `g.returns.push({from:to,to:x.from})` 里变量名互换过一次，实现时以 §5.5 为准，不要照抄变量名。

### 5.6 边界情况清单

| # | 场景 | 期望行为 | 依据 |
|---|---|---|---|
| E1 | **抗贡**：单贡人独有两大王 → `tribute()` 直接 `return`，`phase` 仍为 `'play'`、`returns` 为空 | 走 play 分支；`turn=头游`、`top=null` ⇒ 角标「领出」 | `engine.js:27` |
| E2 | **双贡**：`returns` 含 2 条 | 两张卡同时显示「还贡」——**全局唯一允许 ≥2 个角标的场景**，因还贡本身并行 | `engine.js:29` |
| E3 | **接风**：最后出牌者已走完 → `turn=(winner+2)%4`、`top=null` | 该座位角标「领出」（`place<0`，不误判为已走完） | `engine.js:41` |
| E4 | 对家也已走完 → `turn=next(g,winner)` | 同上，仍为「领出」 | `engine.js:41` |
| E5 | 人类座位在 return 阶段是**进贡方**（末游） | 无角标；`aria` 后缀「等待对方还贡」；`#hint`「等待电脑牌友还贡」 | `engine.js:31` |
| E6 | `turn===i` 且 `top===null` 但人类无合法牌型 | 不可能——无 `top` 时任意单张即合法 | `engine.js:19` (`beats(a,null)===true`) |
| E7 | 出牌后自己走完且 `settle()` 置 `phase='over'` | S0 优先于 S6，`aria` 后缀「本副结束」，名次在 `<span>` 文本中 | `engine.js:33–35` |
| E8 | 双下（`result.double`） | `place>1` 的两位 `<span>` 均显示「双下」，`aria` 后缀「本副结束」 | `app.js:20` |
| E9 | 只剩一家有牌 | 不会发生——`settle()` 在 `finished.length===3` 时即补第四家并结算 | `engine.js:33` |
| E10 | `top.seat===i` 且 `turn===i` | 不会发生——清桌时引擎先置 `top=null` 再定 `turn` | `engine.js:41` |

## 6. 验收判据（供 严守真 复跑）

| # | 判据 | 方法 |
|---|---|---|
| A1 | **不变量**：任意渲染时刻，`chipText(i)!==''` ⟺ 该座位有行动权 ⟺ `.seat.active` 存在 | 404 场景差分，断言 0 违例 |
| A2 | 角标取值域闭合：`chipText(i) ∈ {'', '领出', '轮到', '还贡'}` | 同上 |
| A3 | **`turn===i && phase==='play'` 时角标绝不为「等待」**（K1 直接回归断言） | 构造 `last[i].pass=true` + `top` 存在 + `turn===i`，断言输出「轮到」 |
| A4 | 重新领出：`turn===i && !top` ⇒ 「领出」 | 模拟至三家全过清桌，断言 |
| A5 | 接风：`finished` 含 winner、`turn=(winner+2)%4`、`top===null` ⇒ 「领出」 | 构造验证 |
| A6 | `aria-label` 后缀恒非空，且 ∈ {领出/轮到/还贡/已走完/等待中/等待其他玩家回应/等待对方还贡/已不要，等待中/本副结束/本场结束} | 404 场景全量断言 |
| A7 | 双贡时恰好 2 张卡显示「还贡」；单贡恰好 1 张；抗贡 0 张（此时为「领出」） | 构造三种 tribute 结果 |
| A8 | CSS 中不存在任何以颜色为唯一区分手段的角标状态 | 静态检查：`.turn-chip` 无第二处 `background` 覆盖 |
| A9 | 宽度不回归：≤560px 断点下最长角标（3 字）不超出原「等待」宽度 | 与改动前快照比对 |
| A10 | `.turn-chip` 带 `aria-hidden="true"`；`.seat` 无 `aria-live` | 静态检查 |

### 本地预验证结果（供对照）

将 §5.1 的 `chipText()` / `chipAria()` 原样接入引擎跑 60 副连续对局、**3868 次渲染采样**：

| 指标 | 结果 |
|---|---|
| 不变量违例（角标非空 ⟺ 有行动权） | **0** |
| 角标取值越界 | **0** |
| `aria` 后缀越界或为空 | **0** |
| 旧实现误判为「等待」的次数 | **113**（QA 报 35/404，采样口径不同，同向印证） |

角标分布：`空 2908 / 轮到 820 / 领出 127 / 还贡 13`

`aria` 后缀分布（**10 种状态全部被覆盖**）：

| 后缀 | 次数 | 后缀 | 次数 |
|---|---|---|---|
| 等待中 | 1260 | 已走完 | 189 |
| 轮到，可压牌或不要 | 820 | 本副结束 | 36 |
| 等待其他玩家回应 | 790 | 等待对方还贡 | 13 |
| 已不要，等待中 | 616 | 轮到，需要还贡 | 13 |
| 轮到，领出，不能不要 | 127 | 本场结束 | 4 |

> 观察：「领出」仅占行动态的 13.4%（127 / 947），符合掼蛋实际节奏——绝大多数回合是跟牌。这印证了 §2 的判断：**「领出」是最需要被明确标注、也最容易被 wait-based 误伤的状态**，值得单独一个文案。

## 7. 决策记录与未采纳方案

| 方案 | 结论 | 原因 |
|---|---|---|
| turn-based（行动权归属） | **采纳** | §1.1 四条理由 |
| wait-based（阻塞状态） | 否决 | 与金环互补而非同真同假，冗余通道自相矛盾；依赖 `last[]` 历史反推，结构上易错 |
| 混合：`active` 恒显示「轮到」，「等待」仅用于 return 阶段 | 否决（QA 曾建议） | 方向正确但保留了一个 wait 语义状态位；return 阶段的「等待」完全可由 `aria` 承载，视觉上不需要，留着就是下一个 K1 |
| 领出文案用「必须出」 | 否决 | 丢失「本轮第一个出牌」信息，语感偏命令；且「领出」与 `RULES.md` / `#hint` 同词汇 |
| 给 `<em>` 之外再加「已过牌 / 已出牌」角标 | 否决 | 与 `<em>` 重复，违反 §3.2；且会把角标语义从单布尔退化为多值，重新引入不一致风险 |
| 「已还贡」角标 | 降级为 P2 备案 | §3.3 四条理由 |

---

## 8. 需要用户拍板的两个选项

1. **领出文案**：`领出`（推荐，2 字，与规则书同词汇）／ `必须出`（3 字，义务更直白）。
2. **「已还贡」是否本轮就做**：建议不做（P2 备案）。若要做，需接受「角标 ⟺ 有行动权」不变量被打破、以及 ≤560px 裁切风险上升。
